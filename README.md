# Лабораторная работа № 4: нормализация данных до 3НФ

Практическая работа на MySQL в Docker: аномалии в плоской таблице «заказы — клиенты — товары — представители», разложение данных на четыре связанные таблицы (один заказ ведёт ровно один представитель), проверка переноса, резервные копии и журнал SQL-действий.

Выполняется в связке **VS Code — Git Bash — Docker CLI** (контейнер `my-mysql`, пароль root `123`).

## 1. Что нормализуем

Исходная таблица из задания хранит в одной строке шапку заказа, товар с ценой и представителя:

| Код заказа | Дата | Код клиента | Код товара | Название товара | Цена | Код представителя | Имя представителя | Количество |
|---:|:---:|---:|---:|---|---:|---:|---|---:|
| 5001 | 2026-03-02 | 101 | 201 | Монитор | 15000 | 1 | Соколов Артём | 3 |
| 5001 | 2026-03-02 | 101 | 202 | Клавиатура | 2500 | 1 | Соколов Артём | 5 |
| 5002 | 2026-03-04 | 102 | 204 | Ноутбук | 65000 | 2 | Морозова Елена | 2 |
| 5003 | 2026-03-06 | 101 | 203 | Мышь | 1200 | 1 | Соколов Артём | 10 |
| 5003 | 2026-03-06 | 101 | 205 | Флешка | 900 | 1 | Соколов Артём | 20 |
| 5004 | 2026-03-09 | 103 | 202 | Клавиатура | 2500 | 3 | Гаврилов Павел | 2 |
| 5004 | 2026-03-09 | 103 | 204 | Ноутбук | 65000 | 3 | Гаврилов Павел | 1 |
| 5005 | 2026-03-11 | 102 | 201 | Монитор | 15000 | 2 | Морозова Елена | 1 |
| 5005 | 2026-03-11 | 102 | 203 | Мышь | 1200 | 2 | Морозова Елена | 4 |

Потенциальный ключ строки — `(order_id, product_id)`. Функциональные зависимости:

- `order_id → order_date, customer_id, rep_id`
- `rep_id → rep_name`
- `product_id → product_name, price`
- `(order_id, product_id) → quantity`

По условию **один код заказа соответствует только одному представителю**, поэтому `rep_id` — атрибут шапки заказа (`order_id → rep_id`), а не строки позиции.

Нарушения нормальной формы:

- **2НФ/3НФ** — `order_date`, `customer_id`, `rep_id` зависят только от `order_id` (частичная зависимость от составного ключа); `rep_name` — транзитивно через `rep_id`; `product_name`, `price` — только от `product_id`.
- **Аномалии**: исправление имени представителя затрагивает все его строки; нового представителя или товар нельзя завести без заказа; удаление последнего заказа с товаром стирает и сам товар.

`orders_bad` намеренно не имеет первичного ключа и ограничений `NOT NULL` — так нагляднее показывать недостатки исходной структуры.

## 2. Схема 3НФ

| Таблица | Первичный ключ | Что хранит |
|---|---|---|
| `representatives` | `rep_id` | Код и имя представителя |
| `products` | `product_id` | Товар, название и цена |
| `orders` | `order_id` | Дата, код клиента и **один** представитель заказа |
| `order_items` | `(order_id, product_id)` | Товар и количество в заказе |

В `orders` представитель задаётся внешним ключом на `representatives`: `rep_id` — одиночный атрибут строки заказа, поэтому связь «один заказ = один представитель» гарантируется структурой (в отличие от плоской таблицы, где представителя можно продублировать в разных строках заказа). Клиент хранится кодом прямо в шапке: имени клиента в исходной таблице нет, отдельный справочник не нужен. Каждый атрибут зависит от ключа своей таблицы, от всего ключа и не транзитивно — схема в 3НФ.

## 3. Подготовка Docker и лога

Проверьте контейнер:

```bash
docker ps --filter name=my-mysql
```

Убедитесь, что путь для отдельного лога ещё не занят:

```bash
docker exec my-mysql sh -c 'test ! -e /var/lib/mysql/normalization4_20261118.log'
```

Переключите общий лог MySQL на отдельный файл для этой работы:

```bash
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'OFF'; SET GLOBAL general_log_file = '/var/lib/mysql/normalization4_20261118.log'; SET GLOBAL log_output = 'FILE'; SET GLOBAL general_log = 'ON';"
```

## 5. Демонстрация аномалий

```bash
docker exec -i -e MYSQL_PWD=123 my-mysql mysql -uroot --table --default-character-set=utf8mb4 < sql/02_anomalies.sql
```

- **Обновление:** представитель 1 встречается в 4 строках; переименование требует обновить все строки. Частичное обновление даёт противоречие — у одного представителя два имени:

```
+--------+-----------------------------+-----+
| rep_id | rep_name                    | cnt |
+--------+-----------------------------+-----+
|      1 | Соколов Артём               |   2 |
|      2 | Морозова Елена              |   3 |
|      1 | Соколов А. В.               |   2 |
|      3 | Гаврилов Павел              |   2 |
+--------+-----------------------------+-----+
```

- **Вставка:** нового представителя нельзя добавить без заказа — появляется строка-мусор с `NULL`:

```
+----------+------------+-------------+------------+--------------+-------+--------+-----------------------------+----------+
| order_id | order_date | customer_id | product_id | product_name | price | rep_id | rep_name                    | quantity |
+----------+------------+-------------+------------+--------------+-------+--------+-----------------------------+----------+
|     NULL | NULL       |        NULL |       NULL | NULL         |  NULL |      4 | Кузнецов Игорь              |     NULL |
+----------+------------+-------------+------------+--------------+-------+--------+-----------------------------+----------+
```

- **Удаление:** удаление заказа 5003 стирает и информацию о товаре 205 «Флешка» — оба контрольных запроса возвращают пустое множество (`Empty set`).

Каждая пробная операция выполняется в транзакции и отменяется `ROLLBACK`, поэтому финальная выборка показывает исходные 9 строк без изменений (скриншот `image-1.png`).

## 6. Дамп до нормализации

Лог временно выключается, чтобы служебные запросы `mysqldump` не попали в журнал действий:

```bash
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'OFF';"
docker exec -e MYSQL_PWD=123 my-mysql mysqldump -uroot --set-gtid-purged=OFF --single-transaction orders_norm > dump_before.sql
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'ON';"
ls -lh dump_before.sql
```

В `dump_before.sql` — только исходная таблица `orders_bad` с данными.

## 8. Проверка данных и аномалий

```bash
docker exec -i -e MYSQL_PWD=123 my-mysql mysql -uroot --table --default-character-set=utf8mb4 < sql/04_check.sql
```

Контрольные значения вывода скрипта:

- Суммы `SUM(price * quantity)` до и после совпадают: **307 300.00**, строк **9** и **9**.
- Заказов и строк `orders`: **5** и **5**; товаров и строк `products`: **5** и **5**; представителей и строк `representatives`: **3** и **3**.
- `missing_from_3nf = 0` и `extra_in_3nf = 0` — ничего не потеряно и не добавлено лишнего.
- Соединение четырёх таблиц восстанавливает исходные строки один в один.
- Проверка «один заказ = один представитель»: 5 заказов — 5 строк, дублей нет.
- Тестовые запросы: Соколов вёл 2 заказа, Морозова 2, Гаврилов 1; суммы заказов 57 500 / 130 000 / 30 000 / 70 000 / 19 800; лучший представитель по сумме — Морозова Елена (149 800.00).

Только после этих проверок скрипт переименовывает исходник: `RENAME TABLE orders_bad TO orders_bad_archive` (данные не удаляются). Итоговый список таблиц:

```
+-----------------------+
| Tables_in_orders_norm |
+-----------------------+
| order_items           |
| orders                |
| orders_bad_archive    |
| products              |
| representatives       |
+-----------------------+
```

(скриншот `image-3.png`).

## 9. Дамп после нормализации

```bash
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'OFF';"
docker exec -e MYSQL_PWD=123 my-mysql mysqldump -uroot --set-gtid-purged=OFF --single-transaction orders_norm > dump_after.sql
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'ON';"
```

В `dump_after.sql` — четыре нормализованные таблицы и архив `orders_bad_archive`.

## 10. Экспорт только SQL-действий этой работы

Остановите журналирование и скопируйте выделенный файл из контейнера:

```bash
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'OFF';"
docker cp my-mysql:/var/lib/mysql/normalization4_20261118.log ./general_raw.log
```

Отфильтруйте записи соединений и служебные запросы клиента (скрипт сохраняет многострочные SQL-запросы):

```bash
python sql/filter_log.py general_raw.log my_actions.log
rm general_raw.log
```

Получается 181 строка — только SQL-действия этой работы: от `CREATE DATABASE orders_norm` до `SHOW TABLES`, включая транзакционные демо аномалий (`SET autocommit = 0` … `ROLLBACK`). Служебные запросы `mysqldump` и команды переключения лога в файл не попадают (скриншот `image-4.png`).

## 11. Файлы задания

- `sql/01_create_bad.sql` — создание базы `orders_norm` и исходной таблицы.
- `sql/02_anomalies.sql` — три транзакционные демонстрации аномалий.
- `sql/03_normalize.sql` — схема 3НФ и перенос данных.
- `sql/04_check.sql` — проверки и архивирование исходника после проверок.
- `sql/filter_log.py` — экспорт только SQL-действий из общего лога.
- `dump_before.sql`, `dump_after.sql` — дампы до и после нормализации.
- `my_actions.log` — отфильтрованный лог действий.
